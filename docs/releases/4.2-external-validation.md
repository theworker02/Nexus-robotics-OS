# Nexus Robotics OS 4.2 External Validation Plan

This document separates repository conformance from evidence that requires external systems. A passing contract test never promotes an external validation level.

## HIL validation — L4

**Status: NOT RUN.** Requires a real sensor, controller, or robot component connected through an approved adapter; calibrated limits; independent emergency stop; operator procedure; fault injection; recorded telemetry; and a reproducible report. The current Rust Proving Ground can earn L0/L1 evidence only.

## Live ROS 2 transport

**Status: contract-tested; live transport NOT RUN.** `integrations/ros2` maps known ROS interface types into capabilities and now tests lifecycle, unknown-type rejection, telemetry, and observable stop requests. It does not contain an `rclrs` graph client, subscriptions, publishers, services, actions, QoS negotiation, or authenticated transport. A live test requires a running ROS 2 graph, endpoint owner, bridge configuration, and a safety-reviewed adapter dispatch path.

The committed Gazebo/ROS 2 physics probe is a separate transport assertion. It must not be described as a Rust runtime skill certification until it is driven through the deterministic adapter and Safety Governor boundary.

## External model providers

**Status: NOT IMPLEMENTED / NOT RUN.** No provider client, credentials flow, model registry, or remote request implementation exists in this checkout. Adding a provider requires an explicit optional feature, authenticated transport, privacy policy, timeout/budget handling, schema validation, audit records, deterministic fallback, and a local fixture test. Remote model output must remain advisory and cannot dispatch actuators.

## Live MCP and device transports

**Status: NOT IMPLEMENTED / NOT RUN.** The repository contains policy documentation but no MCP handshake/client/server, BLE, Wi-Fi, MQTT, or device transport implementation. A future connector must be opt-in, permissioned, credential-safe, health-monitored, and tested against a local deterministic fixture before any live endpoint is used.

## Vendor verification

**Status: NOT RUN.** Nori is a community compatibility target; ROS 2 and LeRobot are adapter/bridge surfaces. Vendor verification requires participation or an independently attributable vendor test report. Repository metadata must not label an integration `Vendor Verified` without that evidence.

## Production autonomy claims

**Status: NOT CLAIMED.** Production autonomy requires a defined operational design domain, risk assessment, hardware and emergency-stop validation, recovery testing, observability, operator procedures, security review, and release approval. Nexus remains simulation-first and deterministic-safety constrained. No model, skill, or documentation change may promote a behavior to production autonomy automatically.

## Promotion rule

A release report may replace `NOT RUN` only with an attached command, commit, environment, endpoint or hardware identity, timestamp, raw result, and reviewer. Missing equipment, credentials, vendor participation, or authorization remains an explicit blocker—not a pass.
